# Detached category catalog snapshots

Status: **additive pre-1.0 API candidate; six focused tests await local verification**.

## Scope and usage

`GetCategoryCatalogSnapshot(this IErrorCatalogRuntime)` in
`Afrowave.Toolbox.WhenItFails.Runtime` captures the currently active
**category catalog**. It does not extend the existing runtime interface,
change `GetCurrentContext()`, or mutate source documents.

```csharp
using Afrowave.Toolbox.WhenItFails.Runtime;

var response = runtime.GetCategoryCatalogSnapshot();

if (response.IsSuccess && response.Data is { } categories)
{
    foreach (ErrorCategoryDefinitionSnapshot category in categories.Categories)
    {
        Console.WriteLine($"{category.Name}: {category.DisplayName}");
    }
}
```

`ErrorCategoryCatalogSnapshot` is a sealed, getter-only projection of the
11 current public document fields. `Categories` is a separately allocated
read-only collection of `ErrorCategoryDefinitionSnapshot` instances.
Each category snapshot is sealed and getter-only, capturing the eight
definition fields. All document and definition tags, aliases, parents,
default mappings and metadata are copied into separately allocated
read-only collections or dictionaries. No live `ErrorCategoryCatalogDocument`,
`ErrorCategoryDefinition` or `MetadataBag` escapes through the data.

Metadata keeps case-insensitive keys. Default mappings are copied with
the source dictionary's comparer. This preserves the current lookup
semantics in the detached projection without exposing the mutable
source dictionary.

## Failures and consistency

Uninitialized runtime failures are forwarded without data. If a successful
context response contains no category catalog, the method returns Invalid
with `WIF_CATEGORY_SNAPSHOT_CATALOG_NULL`. Unexpected ordinary capture
errors become a stable `WIF_CATEGORY_SNAPSHOT_FAILED` response without
exception details; `OperationCanceledException` propagates.

The capture obtains a single `GetCurrentContext()` response and then copies
its category data. An already returned result is not changed by a later
context activation or by later edits to the source category objects.
However, it is **not a transactional deep snapshot** when external code
mutates the *same live category document during capture*. Callers should
treat a published context as read-only.

The existing Essentials `Response<T>` envelope remains mutable. This
projection does not contain other supporting catalogs, main definitions,
cross-validation results, runtime status or a versioned JSON wire schema.

## Context identity

`GetCategoryCatalogSnapshot()`, `GetErrorDefinitionSnapshots()` and
`GetCrossValidationSnapshot()` are three **independent** runtime reads.
Successful results from separate calls cannot be assumed to belong to
the same active context if activation takes place between the calls.

A proposed next additive API is a **combined capture** that reads the
active context *once* and derives the separate read-only projections from
that selected reference. That would establish common source-reference
ownership for one capture, but still not prevent concurrent in-place
modification of that reference.

A stable **activation generation ID** is a different contract: it must
be assigned by the runtime when publishing a new activation and must
remain associated with the activated context/status. A new GUID
generated by each snapshot call is merely a capture ID, not a context
generation. Neither this category method nor the existing runtime API
currently provides an activation generation ID. Do not infer one from
the current context's mutable fields or claim that independently
retrieved status and context are an atomic pair.

See [definition snapshots](../Definition-Snapshots/en.md) and
[validation snapshots](../Validation-Snapshots/en.md) for the other
narrow, independent projections.
