# Markdown diskless stress runner

Opt-in .NET 10 application for the real ExchangeHouse forward-only Markdown scanner and optional Blackboard Spectre renderer. It does not create or retain a 1 GiB test file.

## Run

From Toolbox root (examples):

- dotnet run -c Release --project Toolroom/Markdown/Stress -- --size 10M
- dotnet run -c Release --project Toolroom/Markdown/Stress -- --size 100M --seed 42
- dotnet run -c Release --project Toolroom/Markdown/Stress -- --size 1G
- dotnet run -c Release --project Toolroom/Markdown/Stress -- --size 10G --no-render

M and G are binary units (MiB/GiB). The final selected Markdown template is completed before EOF, so reported generated bytes can slightly exceed the requested minimum size. The --seed option selects a reproducible xorshift32 sequence. The --max-heap-mib option sets a sampled managed-heap growth budget (default 256 MiB); --no-render isolates scanning from rendering.

A custom TextReader generates Markdown blocks on demand, with a small set of reusable templates: headings, nested/quoted lists, fenced code, Unicode, inline markup, images/links, a bounded 10 KiB line and table-like content. Output is discarded with TextWriter.Null, never captured into an enormous terminal transcript.

The runner checks contiguous 64-bit UTF-16 offsets, source character totals, UTF-8 byte totals, balanced code fences and sampled heap/working-set memory. It exits nonzero on failure.

## Scope

The existing full-document MarkdownParser and Showcase local Markdown viewer still read complete documents. This new scanner offers bounded-memory classification and fence state, not yet CommonMark-complete multiline semantics. A large stress pass cannot itself certify CommonMark compatibility.

The [dedicated workflow](../../../.github/workflows/markdown-stress.yml) runs 10 MiB by default on matching PRs; manually dispatch 100 MiB, 1 GiB or 10 GiB. Do not claim success at large sizes without a completed run.

See [test details](Docs/Stress/en.md) and [implementation status](IMPLEMENTATION_STATUS.md).

## Low-memory Debian field acceptance

For a terminal-only Debian 13 VM with 1 vCPU and 2 GiB of RAM,
use the reproducible [low-memory acceptance protocol](../../../Docs/Low-Memory-Linux-Acceptance/en.md).
Build the Release application **before** measuring runtime with
`/usr/bin/time -v`. Begin with a 10 MiB virtual stream, optionally
advance to 100 MiB, and record the exact Git commit, maximum process
RSS, wall time and swap usage. The virtual stress runner is not an
end-to-end disk-pager benchmark. No result from that VM is claimed yet.
