# Open Design Questions (Not Yet Decided)

This is a discussion backlog, **not** an implementation plan. Decisions recorded in [Notes](../../Notes.md) should not be silently replaced while implementing a new feature.

1. **Precise contracts and layering:** interface method shapes, assembly/package boundaries and DI ownership; no circular implementation dependencies.
2. **Multi-targeting:** decide whether UnderstandMe ships one `net10.0;net11.0` project, a stable net10 core plus net11 adapter, or both. Native C# union facades must not break .NET 10 plugin consumers. Determine WhenItFails dependency baseline after inspecting release/package compatibility; the current project file still declares 0.1.0.
3. **Job and result schemas:** object identity, source metadata, chunk tracking, multiple alternative results, selected result, lineage and idempotent completion.
4. **Atomic QueueMaster behavior:** ownership/lease rules for buffer refill, endpoint death, retries, buffer hand-off, fairness across clients, and starvation prevention without breaking small FIFO buffers.
5. **Synchronous localizer versus live async translation:** explicit API and timeout design, avoiding unbounded waits.
6. **Placeholder protection:** per-backend/language validation experiments for HTML, tokens, difference-based restoration, AI repair; escaping and literal braces.
7. **Storage/retention:** EF Core provider and migration strategy, history deletion guarantees, audit-retention limits, backup/recovery and confidential-content policies.
8. **Chain configuration:** schema, composition UI, compatibility checks, versioning of prompts and profiles, multi-step results and optional branches.
9. **Human queues:** long-run reservations, disconnection, reassignment, and manual correction permissions.
10. **Messenger and security:** durable event vs telemetry guarantees, authorization for per-client SignalR subscription, public aggregate privacy, replay and acknowledgment.
11. **Source format plugins:** model detection for flat/structured JSON and SQL; conflict-safe writeback, allowed filesystem roots, extensibility for AJIS.
12. **Verification before coding:** define unit/integration tests for queue transitions, exact placeholder multiplicity, recovery, editing audits, optional AI checks and .NET 10/11 compatibility.

13. **Native translation feasibility:** prototype .NET-to-CTranslate2 interop; measure baseline Argos/LibreTranslate versus a constrained native worker on a small VPS; test model loading, tokenization, segmentation, concurrency, crashes, independent process restart and failover.
14. **Attribution and licenses:** resolve the individual Argos model-package license/provenance/redistribution question, required third-party notices, and which improvements to propose upstream to LibreTranslate/Argos/CTranslate2.

15. **AfroLT service design:** keep LibreTranslate for HTML/placeholder workflows; decide the independently implemented service's HTTP compatibility surface, capability advertisement, default HTML fallback, and how model health/restart are exposed.
16. **AfroLT WebUI and OpenAPI:** define externally sourced CSS/theme policy, access control of instance settings, Scalar API reference publication policy, and OpenAPI 3.2 versus 3.1 client compatibility.

17. **Versioned reference paths versus API versions:** prototype stable Scalar/spec routes and older-client compatibility tests; separately version the actual HTTP API and define deprecation terms.
18. **Translation improvement feedback:** reviewable `/suggest`-compatible input, source-based AI/human approval, audit and consent/provenance, abuse controls, immediate translation-memory overrides and separately curated model training.
19. **Cross-platform interoperability:** test non-.NET, legacy HTTP clients and optional LibreTranslate-compatible DTOs and endpoints; document stable JSON/error contracts.

20. **AfroLT standalone packaging and optional adapters:** ensure zero dependency on UnderstandMe/Afutrans, small embedded-core deployment, optional self-hosting and SignalR host assemblies, and one authoritative internal translation service.
21. **SignalR contract:** choose versioned hub route and method/event DTOs, JSON default versus optional MessagePack, bounded batch/stream semantics, reconnect/reconciliation, authentication/tenant isolation, quotas, cancellation and idempotent job acceptance.

22. **Shared transport-neutral command contracts:** choose minimal typed command handlers and caller context; define the exact request/response DTO and error representation shared by direct .NET, REST and the single SignalR Hub; verify REST/Hub parity and separate transport envelopes without duplicate business logic.

23. **AfroLT admin Hub:** specify auth and per-tenant visibility for \`/admin\`; current status snapshot and event contract (success/failure, worker/model state, recovery, capacity), subscription filters, bounded fanout/backpressure, event ordering and privacy; separate durable operational/audit records from ephemeral SignalR notifications.
24. **Admin command security and parity:** define which privileged administrative actions are exposed and ensure admin Hub, REST and direct .NET entry points invoke the same authorized application command handlers rather than duplicating work or involving passive Messenger as a scheduler.

25. **Hierarchical SystemMonitor contract:** define the shared typed event envelope, sender and event IDs, filters and access controls for `/SystemMonitor` and `/{ModuleName}/SystemMonitor`; verify one source event fans out to both routes without unrelated events or duplicated publications.
26. **Cross-host aggregation:** optional explicit bridging between separate processes, with origin preservation, deduplication, security and loop prevention. No automatic federation by matching route names.
27. **Monitor reliability tests:** zero listeners, slow/disconnected clients, privacy-safe diagnostics, bounded nonblocking fan-out, and no effects on business commands or durable writes.

28. **Typed monitoring payloads:** settle the MonitorEvent<T>/Message<T> generic interface and contract registry, including stable wire ContractId/SchemaVersion, System.Text.Json serialization for different T, unknown models, .NET 10/11 and cross-language client compatibility.
29. **Passive listener parity:** validate that the dedicated module transmitter and aggregate event-router listener each receive the same logical generic event, maintain its original payload model, and cannot delay or disrupt the publisher.

30. **Optional remote monitoring client:** specify configurable remote URLs, authentication/trust, source filters and a long-lived SignalR client reconnect policy for VPS3-style multi-host aggregation; do not make remote reception mandatory.
31. **Federation metadata and safety:** preserve the original typed event, origin and EventId, define optional relay path/hop metadata, per-source health reporting and bounded deduplication/loop prevention for chained or reciprocal connections.
32. **Cross-host contract tests:** simulate two remote monitors feeding a third, disconnect/reconnect with gaps, module-scoped filtering, unknown generic payloads, malicious/untrusted senders and bounded fan-in without blocking local work.

33. **Lite SystemMonitor handshake:** finalize which identifying GUIDs/metadata travel at SignalR connection establishment and which fields the source announces via `MonitorHello` (node name, modules, typed contract versions and instance metadata).
34. **Known-node checks:** define the receiver's configured endpoint + expected NodeId registry, module/source consistency checks and expected behavior for unknown/mismatched nodes, including optional relay-source declarations.
35. **Threat-model boundary:** accept that GUID is a public identifier, not cryptographic authentication. Test trusted HTTPS endpoint/certificate validation, explicit receiver configuration and absence of any remote client-callable Publish method; keep stronger credentials optional if requirements change.
36. **Monitor identification tests:** connection announcement precedes normal events, unknown GUID is rejected/ignored, misdeclared event source is not forwarded, and failures never block local work.

37. **Monitor node self-enrollment:** finalize the small separate HTTPS request endpoint, `ClientId` + declared source metadata, durable pending registration record, and typed non-secret `MonitorRegistrationRequested` notification to live administrators. Never auto-approve.
38. **Admin decision and client claim:** define authorized approve/deny UI and audited decision, recipient-generated GUID `ClientKey` bound to the approved client/source permissions, safe one-time applicant claim/poll flow after offline approval, replacement/revocation and HTTPS headers for subsequent control calls. Do not publish the key on SignalR.
39. **Enrollment/source-direction clarity:** distinguish the credential used on VPS4 -> VPS3 enrollment/control from VPS3 -> VPS4 read-only SignalR monitoring; configure and validate remote server identity independently. Approval may start automatic source monitoring without changing the outgoing-only Hub.
40. **Enrollment tests:** concurrent/duplicate requests, administrator absent/present, rejected and approved nodes, secret-claim theft, expired claim tickets, registration flooding, and rejected/failed remote connection without impacting existing monitoring or other work.

41. **Adaptive monitor familiarity:** define the small approved-node connection profile (ClientId, configured HTTPS endpoint, stable versus changeable network hints, module list); distinguish active connections from newly established/reconnected sessions and document the deliberate spoofing risk of accepted unchanged-looking connections.
42. **On-demand GUID challenge:** define which changes trigger `IdentityChallenge`, where HTTPS challenge/response occurs outside the event-only Hub, challenge expiry and connection binding, and how the recipient compares the private recipient-issued ClientKey before forwarding data.
43. **Compatibility and risk-level tests:** known routine reconnect with only ClientId, changed IP behind NAT/proxy, changed source-module claims, successful/failed/no response to the GUID challenge, spoofed familiar headers/IP, plus optional challenge-every-session policy for stricter deployments. No scenario may stop core work.

44. **Interactive administrator filters:** finalize independent multi-select source/VPS, module/instance, event type/severity, correlation/job, full-text/diagnostic and time filters; include saved personal presets, default views, reset, and performance with large incoming event rates.
45. **Incident-and-discard on bad input:** define admission validation and durable incident schema; invalid/mismatched event is dropped, its registered source is **never blocked automatically**. Distinguish new legitimate Pending registrations from rejected regular event input.
46. **Admin-only node decisions:** define read and manual controls for incident review, view-only Mute, ingress Block, revocation and disconnect; ensure no automatic sanctions are triggered by counts of incidents.
47. **Robustness tests:** per-admin UI filters do not affect other admins or source feeds; repeated incidents aggregate safely, invalid messages do not enter normal streams, unaffected nodes stay live, and ingestion quotas shed load without changing trust state.

48. **Provider priority vs job priority:** define minimal endpoint capabilities and the Pipe-owned selection policy; verify independent QueueMaster P0-P4 dispatch and provider order/cost ranking, including configurable Google-first and LibreTranslate-first profiles.
49. **Provider cost model:** define per-character/token/request/local compute estimates, handling unknown prices/currencies, spending caps, quota/latency constraints, and whether costs are recorded per job/step/target; explicitly avoid assuming local translation has zero cost.
50. **Escalation/fallback decision:** define exact retryable failures versus validation-based escalation and mandatory AI/human review; determine attempt limits, per-endpoint cooldown, ambiguous timeout retry billing/idempotency and fallback exhaustion outcomes.
51. **Provider override hierarchy and privacy:** settle global -> Pipe -> Translation Target -> allowed job/Chain-step precedence without relaxing source/target language, format/HTML, protected placeholders, LocalOnly, forbidden remote providers or budget caps.
52. **Provider routing tests:** primary compatible provider, unsupported pair/capabilities, endpoint not ready, LocalOnly never calls external APIs, paid-primary preference, cost-first preference, budget rejection, validation failure escalation, exhausted providers and independent monitoring of attempts/cost estimates.

53. **Mandatory RealTime edge cases (baseline agreed):** Mandatory selects an available eligible engine without waiting for its preferred busy provider, while non-Mandatory RealTime can return untranslated source and update segments later. Define exact no-endpoint and maximum-cost outcomes, deadline and optional continuation cancellation policy; never imply that Mandatory bypasses limits.
54. **SystemPersistent bounds (baseline agreed):** opt-in bounded, persistent, context-aware approved translation memory is checked before providers and remains separate from authoritative dictionaries and provisional cache. Decide concrete key schema, read/write flags, quotas, promotion/approval, invalidation and deletion.
55. **Provider routing dry-run (deferred):** admin-side simulation is a useful future enhancement but is explicitly **not required for the first implementation**. Revisit after stable selection/Settings contracts, with no paid work performed during a dry run.
56. **Immutable Settings at request creation (baseline agreed):** changed admin defaults apply to new requests, queued/in-flight items retain their captured policy; orchestrator pause/stop overrides execution. Settle public typed Settings groups, valid flag combinations, snapshot storage/version, explicit cancellation/revoked credential behavior and request-bound deadline semantics.
57. **Version-aware capability tests (baseline agreed):** verify endpoint language/format/placeholder behavior and re-evaluate when the detected model version changes. Decide probe corpus, cadence, capability-result TTL and avoiding charged self-tests unless explicitly permitted.
58. **Manual language-pair preferences (baseline agreed):** default engine tiers free/local -> equally ranked paid APIs -> AI, with operator overrides per language pair and without automatic historical quality ranking. Define deterministic tie-breaking among eligible same-tier providers and a stable configuration/override representation.

59. **Segmented live updates:** define `RequestId`, ordered `SegmentId=0..N`, source-format boundaries, partial results in arbitrary completion order, duplicate/outdated results, HTML block versus inline DOM wrappers, safe plain-text `textContent` versus validated HTML insertion and application delivery/reconnect/cancellation separate from SystemMonitor.
60. **Flags versus enums:** name the independently composable request behavior flags (especially Mandatory and SystemPersistent read/write), exclusive QueuePriority and wait strategy, and validate meaningful combinations without a monolithic options object.
61. **Orchestrator command precedence tests:** queued/running request retains old policy when global rankings change; administrative pause stops new dispatch even for Mandatory; later resume uses captured request settings rather than newly chosen provider priorities.

62. **UI-neutral segmented results (clarified/agreed):** splitter identifies ordered text/format segments and returns `RequestId + SegmentId` completion messages. Blazor, JS, Avalonia etc. select their own display mechanism; finalize revision/out-of-order update and safe formatting adapter contracts without imposing DOM/JS on core.
63. **Provider pricing model and account plans (agreed):** provider adapters declare charging units/metering capabilities; each configured account/endpoint carries actual prices, purchased package, included usage (e.g. 1,000,000 words/month), currency and renewal information. Decide field schemas and how provider-specific word/token counting and unknown price data are represented.
64. **Account quota policy (agreed):** administrator chooses hard cap, explicitly capped paid overage or waiting for an independently purchased/registered additional package. No automatic buying or raising cost ceilings. Specify billing period/renewal/rollover and event/notification thresholds.
65. **Concurrent quota accounting:** settle durable accounting ledger, per-attempt atomic reservation before billable dispatch, actual-vs-estimated settlement, provider timeout/unknown-charge behavior and cross-VPS coordination for shared provider accounts. Hard spending gates must respect current authorized account limits even for queued jobs under older provider-preference snapshots.
66. **Provider billing and reporting tests:** exhausted package and fallback, hard cap under concurrent dispatches, correct overage price and max, manual add-on verification, renewal and time zones, paid timeout/retry uncertainty, quota warning events with durable usage independent from SystemMonitor, and estimated/actual cost labels.

67. **Orchestrator-owned admission (agreed):** the caller suggests provider and behavior, but the orchestrator applies stronger admin/system constraints, preserves the original request, creates an effective policy snapshot and reports meaningful adjustments. Define typed admission receipt, rejection/failure reason codes and mapping to existing Essentials/WhenItFails result contracts.
68. **Authorized alternative before rejecting (agreed):** a forbidden, exhausted, unsuitable or unavailable client-preferred provider must trigger evaluation of other eligible permitted providers by default. A request is rejected only when no feasible authorized route exists; after acceptance it can fail explicitly if no longer feasible. Tests: Google requested but prohibited -> LibreTranslate used; Google over hard quota -> alternate; no suitable provider -> clear reason.
69. **Provider preference versus hard requirement:** finalize which request fields denote suggestions versus true non-negotiable language, format, privacy and maximum-cost constraints; prevent a `Mandatory` flag or caller-supplied priority from bypassing operator policy. Explicit admin queue pause always takes precedence.
70. **Admission receipt versus execution result:** distinguish Accepted/Deferred/Rejected at submission from Completed/Failed after work, report `RequestedProvider`, effective policy adjustment codes and `UsedProvider` only after actual execution; allow per-segment provenance when different engines are used.
71. **Operational caps at dispatch:** preserve historical effective preference for accepted jobs while applying current hard account limits, endpoint ability/health and admin stops before **new** calls. Define nonblocking fallback/deferral/failure behavior when a once-eligible paid account becomes unavailable and prevent extra charges beyond the cap.

72. **Client policies and default (agreed):** add optional, named per-client/group translation permissions and quotas, with **unrestricted provider selection at the client layer by default for known clients**, constrained by global admin/real provider limits. Public/anonymous API access is opt-in and uses a separate **fully configurable** profile: free/local-only is just one template, while explicitly funded paid/AI or fully open public access is also permitted by administrator decision. Resolve precedence, per-client overrides and disabling.
73. **Client admission/fallback (agreed):** an external caller's requested paid Google/AI API cannot bypass verified ClientPolicy. If forbidden, the orchestrator selects a compatible provider allowed to that client and reports the normalization; reject with a precise reason only when none is available.
74. **Shared paid account versus client quota:** finalize authoritative per-client metering, time windows, atomic dispatch reservation for both independent client and provider limits, reconciliation, billing-attempt provenance, and cross-host consistency.
75. **Optional public spare capacity:** define admin-configured public API exposure, trust boundaries/API identity (distinct from lite SystemMonitor GUIDs), anonymous free tier, per-client rate/concurrency/max input controls and internal-capacity reservation/fairness without separate per-client QueueMaster queues.
76. **Client policy updates and tests:** client entitlement narrowed while old work is queued; paid client allowed until its own quota or provider account quota is exhausted; unauthorized Google request falls back to LibreTranslate; public clients on a free-only profile cannot spend API budget; explicitly operator-funded public paid access must respect its shared profile/global budget and configured capacity controls; spoofed ClientId cannot impersonate an entitled paying client.

77. **Mandatory human provider capability (agreed):** support a fully functional Human translation worker and manually supplied result without **any** machine/AI engine installed. All other providers are optional individually activated plugins. Finalize the minimum human worker registration/assignment/approval contract without assuming a particular UI or online availability.
78. **Human-only outcomes and timing:** test manual translation accepted/pending/completed, no human currently ready, RealTime/Mandatory deadline and original-text fallback; no automatic translator or mandatory AI/human review step should be silently added.
79. **Opt-in public API entitlement is configurable (agreed):** public API endpoint exposure itself must be explicit, but its public/anonymous client profile can allow free-only, human-only, selected paid/AI or all globally activated providers. Prior free-only examples are defaults/templates, never hard restrictions. Test a philanthropic all-access public policy constrained by admin-configured total budget, and a closed/local/human-only installation.
80. **Optional plugin/activation boundaries:** confirm provider ranking does not instantiate providers, that absent paid/AI accounts create no package/credential dependencies, and that a host with Human as its sole supported active provider can run all applicable core workflows.

81. **Durable Human backlog (agreed):** accepted human-intended translation tasks must persist independently of translator interface availability. A translator who opens a UI later sees counts by the **same five QueueMaster priorities** and compatible languages, and claims work without a separate human-owned queue.
82. **Human claiming and recovery:** finalize exclusive atomic claim/lease timeout, heartbeat or voluntary release, reconnect after prolonged absence, safe stale completion prevention and draft persistence. Ensure two simultaneous translators cannot publish a conflicting completion.
83. **Human backlog snapshot and UI:** define trustworthy waiting/claimed/in-progress counts by priority and language for each authorized translator, efficient filtering/selection, current-state reloading on login and updates after notification loss. Do not treat SignalR SystemMonitor as the queue store.
84. **P0 versus explicitly submitted Human tasks (corrected baseline):** P0 is automatic-only, inactive in Human-only installations, and never creates a Human continuation. Durable P1-P4 manual work requires independent authorized submission; test long offline waits, crash/restart recovery, deadline/cancellation, missing human worker and immediate original-text P0 response.

85. **Strict P0 provider separation (agreed):** `RealTime`, even `Mandatory`, can only select activated automatic engines; no Human fallback is allowed. If only Human is configured, disable P0 processing and return the unchanged source almost immediately. Test mixed and Human-only hosts and fallback after all machines fail.
86. **Private RealTime content boundary (agreed):** no RealTime text (including private chat content) may enter durable Human work, translator UI or manual review through any automatic path. Human processing needs independently submitted and authorized non-P0 durable work. Verify no hidden retention, manual queue population or exposed Human candidate on error paths.
87. **P0 inactivity and observability:** represent P0 as inactive in Human-only mode without creating a sixth queue or implying pending manual work; clarify immediate untranslated response status and safe monitoring counters with no chat text. Validate that enabling/disabling optional automatic engines refreshes P0 eligibility without touching existing manual backlog.

88. **Request Privacy is independent (agreed):** define `Privacy` separate from `Persist`, `CachePolicy`, `LifeTime`, P0-P4 priority and provider routing. A Private translation can be stored for authorized chat/forum history reuse; source/target/administrator policy may tighten, never silently weaken, effective privacy. Finalize enum/type and inheritance rules.
89. **Private scoped result storage (agreed):** persist verified private translation results in a viewer-authorized host-owned or adapter-backed cache **without persisting volatile P0 jobs**. Choose tenant/conversation/source-message+revision/culture/format key, retention/deletion coupling, safe deduplication within scope, and behavior on source edits, deletion and group membership changes.
90. **No third-party manual privacy leak (agreed):** Private content must not enter external Human worker queues, third-party auditor/administrator content UI, global SystemPersistent memory or application dictionary `KEY=VALUE` registration. **A recipient who can already view their own message translation may voluntarily self-correct it through the consuming app; this is not third-party manual audit.** Existing audit of actual manual authoritative dictionary edits remains mandatory but does not authorize manual inspection of Private chat translations. Test monitoring, errors and editor history contain no private text.
91. **Private providers and access tests:** finalize user/client/target privacy restrictions on external cloud/AI processing, privacy-tightening admission, current authorization on every stored-translation read, cross-tenant and cross-chat isolation, source revision invalidation, deletion/TTL, participant removal and zero repeat provider calls on authorized unchanged history reads.

92. **Chat vs UI dictionary boundary (agreed):** `KEY=VALUE` and dictionary-less source registration exist exclusively for app/web UI localization dictionaries (JSON, other glossary stores), not dynamic chat/forum messages. Temporary Splitter IDs `0..N` are request-scoped and must **never** become durable dictionary/cache keys.
93. **Chat application owns complete results (agreed):** the engine returns translated chunks/results, the consumer reassembles the final message, chooses whether to save it with source history, controls source-message identity, current reader permissions, source revision and retention. No mandatory UnderstandMe chat database or persisted splitter IDs; P0 remains volatile.
94. **Recipient self-correction (agreed optional):** an authorized recipient can correct their own translated message in a host UI without dispatch to a Human translator, general manual audit or shared dictionary. It must not alter another user's translation or the original author text. Finalize optional UI/edit/override contracts.
95. **Optional corrected-translation cache (agreed):** recipient can decline caching and use correction only for current view, or opt into saving an owner/message/culture-scoped override. Broader publication or shared-memory contribution is a distinct explicitly authorized decision, not implied by cache. Test no-cache=no durable correction, personal cache isolation, source revision changes and original host history cache independence.

96. **Semantic Splitter default rules (agreed):** small texts can remain one chunk; for longer plain text prefer paragraphs when recognizable, otherwise sentence boundaries; `Settings` can select paragraph/sentence. Markdown and HTML use their text-bearing structural content, preserving formatting/context. Other formats gain specific splitters only when needed.
97. **Plain-text segmentation details:** determine what one newline versus blank lines means for each input type; sentence boundary rules must not break decimal numbers, URLs, abbreviations, quotations or language-specific punctuation. Test reconstruction of whitespace, paragraph separators and punctuation.
98. **Markdown/HTML grouping:** decide exact Markdown AST node grouping, HTML nested inline text grouping, non-translatable elements and metadata for safe content placement; preserve code, links, placeholders and original markup. Avoid one-word chunks caused by formatting tags.
99. **Oversized semantic units and context:** set provider max-length fallback order (further safe split or other eligible engine), context preservation/strict boundaries, and how to report a unit too large without truncation. Verify request-local chunk IDs remain ephemeral and no dictionary or chat history keys are generated.

100. **Structural template + source-filled ResultList (proposal):** keep parsed HTML/Markdown structure plus temporary `SegmentId=0..N` slot mapping. Initialize slot values to source content and progressively replace verified completions so partial failures still render the original. Determine `OriginalText` versus `CurrentText` model, status, revision, duplicate/out-of-order completion handling and efficient rendering.
101. **HTML parsing and element mapping:** decide parser/AST interface, how void `br`/`img` and malformed HTML are handled, whether to use separate `SegmentRef` metadata rather than mutating real HTML attributes, and text-bearing attribute translation. Avoid collisions with actual `placeholder` attributes.
102. **Nested inline markup versus sentence context:** design protected inline formatting markers and mapping for mixed content such as `<p>Hello <strong>beautiful</strong> world!</p>`; avoid translating each DOM text node as an unrelated word and validate reconstructed safe markup.
103. **Result projection and hosting:** define minimal UI-neutral projection contract for HTML/Markdown/desktop updates, source fallback on failed chunks and ephemeral cleanup. Do not turn a ResultList into a persistent chat database, QueueMaster work queue or `KEY=VALUE` UI dictionary.

104. **Inner-phrase variants + full-context translation (new proposal):** translate the contents of a nested inline tag (including supported alternatives), then the full containing phrase without formatting tags; match an unambiguous target-language span and reconstruct the original allowed tag around it. Define whether candidate requests are synchronous, parallel or omitted if a provider supports validated inline markers.
105. **Target-language alignment:** define whole-word/phrase matching with case/Unicode handling and language-aware morphology for e.g. Czech `krásný` vs `krásného`; handle multiple identical occurrences, paraphrases, changes in order, untranslatable text and supported variant provenance; never place a tag on an arbitrary match.
106. **Markup hierarchy and safe fallback:** test nested/overlapping/crossed target spans, multiple inline tags, links/semantic attributes versus cosmetic formatting, source-preserving behavior for functional structures and explicit `FormattingUncertain` results for cosmetic losses. Validate safe HTML/Markdown reconstruction and source-first result slots.
107. **Cost/priority/privacy tradeoffs for formatting:** alternative inner translations add quota/latency/cost, may be unsupported by some provider adapters, and must obey every active client/account spending/privacy limit. Evaluate a protected-marker or supported HTML mode before mandatory multi-call processing, with bounded retry and no P0 Human fallback.
